# Audit refresh — 2026-08-25 (branch `main`, HEAD `15c0ef4`)

This audit brings the formal-verification and review record up to the current protocol. Since the
last Lean-backed audit (`audit28-06-2026.md`, cut at `feat/channel-api-impl`) the spec gained four
sections — **§O Falcon-512**, **§P aggregated inter-channel rounds**, **§Q dynamic co-signer
membership / key rotation**, **§R proving locus** — and ~165 commits landed, 77 of them
fund-impacting. None of §§O–R is covered by any Lean model, and one of them **contradicts a
theorem that is still in the audited corpus**.

This document has three parts:
- **Part 1 — Coverage map**: what the current protocol is, and exactly which parts any Lean model
  or prior audit actually covers.
- **Part 2 — Root-cause analysis**: why the vulnerabilities fixed since 2026-06-28 (publicly
  derivable co-signer keys, the 1-of-N drain, skipped/disabled ZKP verification, the gate-8 class)
  were not caught by the audits that existed at the time.
- **Part 3 — Verification plan**: the Lean work this refresh commits to — member-set updates / key
  rotation (§Q), the close lifecycle cases, partial withdrawal, and the inter-channel credit path
  — staged, with the liveness-shaped obligation the gate-8 retrospective demands.

Method: read the code and the existing Lean at HEAD `15c0ef4`; every claim cites `file:line`. This
part (Part 1 + Part 2) is a review deliverable; Part 3 lands as subsequent commits.

## Part 1 — Coverage map (protocol § → verification status)

Two independent, **unlinked** Lean developments exist. Neither is run by CI (`lake build` appears
nowhere in `.github/workflows/`); both are hand-written transcriptions kept in sync by review
discipline, not by extraction or shared vectors.

- **A. `doc/architecture-audit/*.lean`** — the *protocol/spec* model (4 files, 206 theorems):
  `ChannelSafety.lean` (v1, 3 fixed plaintext members), `ChannelSafety2.lean` (Regev→plaintext
  abstraction, tagged sigs), `ChannelSafety21.lean` (bulk + the §M batch fold), `ChannelSafetyMT.lean`
  (§N multi-token, phase 0). Models `abstract*.md`, **not** the Rust. Trust base A1–A6 + abstractions
  M1–M8 disclosed in each file header; **liveness explicitly out of scope** (`ChannelSafety.lean:65-67`).
- **B. `doc/audit/zkp/`** — the *implementation* model (45 files, ~256 theorems): line-by-line Lean
  of the Plonky2 circuits and the L1 contracts, each conjunct citing `source.rs:line`. Excludes

### The specific gaps (asked directly)

- **(a) Close lifecycle — fragments only, split across both projects, no state machine.** Spec side
  has an abstract `CloseGame` + version-max `finalize` fold (`ChannelSafety.lean:647-670,721`)
  giving `challenge_latest_wins` / `end_to_end_close_safety`. There is **no intent / cancel / status
  / deadline machine** — time is only "highest version wins". Contract side *lists* `requestClose`
  / `submitCloseIntent` / `cancelClose` / `finalizeClose` as "STATE MACHINE … no ETH moves"
  (`Coverage.lean:143-152`) — categorized, not proved. `audit28-06-2026.md:369-373` states the
  position: channel-fund safety is captured by the payout *cap*, "not the close/claim proof
  semantics."
- **(b) Partial withdrawal — L1 gate only.** `Contracts/ChannelSettlementManager.lean:125-166` models
  submit/finalize/cancel with theorems `finalizePartial_mints_only_pending` (:303),
  `partial_chain_key_single_use` (:325). **Zero channel-state modeling** — `grep partial` over the
  spec `.lean` finds only partial *receive*. `cancelPartial` is *defined without a theorem* (:216).
- **(c) Member-set changes — modeled nowhere; the only relevant theorem asserts the opposite** (a).
- **(d) Inter-channel credit — partial, and the weakest link.** `interChannel_conservation_bound`
  (`ChannelSafety2.lean:464`) proves joint conservation *given* commitment injectivity, but the
  **double-credit prevention of the same settled tx is explicitly unmodeled** (`lean-safety-proof2.md:97-99`),
  and F-AUX-1 (inter-channel `aux_data == tx_leaf_hash`) is enforced off-circuit at co-sign, "not
  in-circuit" (`audit28-06-2026.md:343`).

**One-line coverage summary:** Lean proves (in-channel batch fold + bulk send/receive accounting +
multi-token frames) on the spec side and (rollup escrow + stake + manager payout cap +
partial-withdrawal L1 gating) on the implementation side. **Close lifecycle, cancel, member-set
updates, Falcon, and §P aggregation fall in the hole between the two projects** — and every one of
the three features this refresh targets lands in that hole.

## Part 2 — Root-cause analysis: why the audits missed them

Since the 2026-06-28 audit, the fixes below were all merged. Each was **green in the local test
suite at the time** and sat inside the declared audit scope, yet none was caught. The causes cluster
into four mechanisms; `why-gate8-was-missed.md` already measured the largest one.

### 2.1 The vulnerabilities, by class

| # | commit | defect | class |
|---|---|---|---|
| V1 | `898a586` (2026-08-12) | **CRITICAL: every co-signer private key publicly derivable.** `keys_for(seed) = MemberKeys::generate(StdRng::seed_from_u64(seed))` with a constant `CLI_COSIGNER_SEED_BASE` in a public repo, no env override, keys not even channel-separated (ch7 slot 0 == ch8 slot 0). Full custody + balance decryption. | (C) out-of-model trust boundary |
| V2 | `e492cec` / `b9cd1ed` / `c2b69fb` (2026-08-15) | **1-of-N drain.** A single co-signer (slot 0), holding only their own Falcon key and the prev state, produced a fully-verifying validity span advancing the channel — the validity circuit verified a *single-signature* list, not the N-of-N. Demonstrated on real pre-fix code (worktree at `c2b69fb`). | (B) the verified statement was weaker than assumed |
| V3 | `898a586` / `eb93e5d` (2026-08-12) | **Skipped / disabled ZKP verification.** `verifySpecialClose` / `verifyLateOutgoingDebit` were forgeable keccak stubs, inert only because a later manager gate happened to revert; `degreeBits==0` MLE bypass; withdrawal VK never initialized on any real deploy script (`doc-vs-code-exit-sweep.md` F1). | (A/D) fail-closed masked a non-running check |
| V4 | `4574348` / `eb93e5d` / F6-F7 | **gate-8 class: honest exit impossible.** post-close-claim and cancel-close unusable on every real deployment; close-after-deposit-import refused. Soundness-perfect, exit-fatal. | (A) liveness axis had no coverage |
| V5 | `061a8c5` / `9c02a2e` (2026-08-15) | registering a delegate as a co-signer silently widened the signed set; registration did not constrain `delegate_count == 0`. | (B) statement weaker than assumed |
| V6 | `d574a2f` / `4da7ee1` | stale fixtures: the checked-in proofs verified against a **superseded VK**, so the green suite proved nothing about the deployed circuit. | (D) the test oracle was not the production object |

### 2.2 Four mechanisms — why the scope had no edge on them

**(A) The corpus formalises only the anti-liveness direction.** `why-gate8-was-missed.md:184-215`
counted, across 44 Lean files / 263 declarations: **174 soundness-shaped, 20 anti-vacuity, 69
structural, 0 liveness / honest-exit.** Nine theorems prove a call *must revert*; none prove an
honest user *can* exit. A scope drawn on the soundness axis ("can an adversary get a false statement
accepted?") is by construction blind to the opposite failure (V3, V4): a check that never accepts a
bad proof while making the honest path impossible. `eb93e5d`'s own message names it — *"a threat
model that only asks 'can an adversary get a false statement accepted?' cannot see these by
construction: they are the opposite failure. Five turned up this week, every one with a green test
suite."* Verdict (`why-gate8-was-missed.md`): **"this codebase systematically treats fail-closed as
a synonym for safe."**

**(B) "Manually reviewed" and "categorized" were read as "verified".** The close state machine,
`verifySpecialClose`, and the whole channel-fund close/claim semantics were **listed** in
`Coverage.lean:143-152` / `:113-124` as STATE-MACHINE or CRYPTO-ORACLE buckets — explicitly *not
proved*. V2 (1-of-N) and V5 (delegate-as-cosigner) lived in the validity-circuit member-set binding,
which the 2026-06-28 audit left uninterpreted ("channel-reg internals … uninterpreted",
`audit28-06-2026.md:369-373`). The audit *said* this plainly in its Limitations; the gap was that no
headline summary carried the qualifier forward, so a reader saw "Lean-backed" and not "…except the
part where the bug was." `audit02-07-2026.md:13-16` found exactly this: "several headline claims
exceeded what was machine-checked."

**(C) The trust base was assumed, never checked against the code.** V1 (derivable keys) is not a
soundness *or* liveness bug in the model — it is assumption **A3 (honest-member key custody)** being
false in the implementation. No audit artifact checked that the CLI's key derivation actually
honored A3; `MemberKeys::generate` from a public constant silently violated it. The Lean trust base
(`ChannelSafety.lean:16-63`) is a list of *premises*, and nothing tested that the deployment
satisfied them.

**(D) The test oracle was not the production object, and CI did not exist.** V6 (stale fixtures) and
the `degreeBits==0` bypass passed because the suite verified against a mock/superseded VK, and
`CloseLifecycleE2E.t.sol:244-252` asserts coverage using a **mock verifier** — true on the soundness
axis, misleading on the liveness axis (`why-gate8-was-missed.md`). Until `63e9087` (2026-08-15)
**the repo had no CI at all** — "no .github, no Makefile, nothing" — so a green *local* suite was the
only gate, and every fund-impacting defect of that week was green in it. `63e9087` added the checks
"that would have caught this week's defects": pinned-submodule integrity (the ExponentiationGate
evaluator was uncommitted inside the pin — working copy built, clean clone did not), `forge build
--sizes` for EIP-170 (elsewhere masked by `--code-size-limit 50000`), and gate-ids DERIVED from the
Solidity.

### 2.3 The recommendations already written down and not yet enforced

`why-gate8-was-missed.md:501-582` names three; none is a property or test yet:
- **R1 Honest-Exit Availability** — for every escrow, a theorem "an honest user can always reach
  their funds": the missing axis. Zero such theorems exist today.
- **R2 real-proof on-chain test per verifier-gated entry point** — no mock verifier in the oracle
  role; V6 and the unset-VK class die here.
- **R6 make the oracle boundary carry an obligation** — a "crypto oracle" or "state machine"
  categorization must emit a discharge obligation (a differential test, a real-proof test), not a
  silent exclusion; V3's forgeable stubs die here.

### 2.4 Direct consequence for this refresh

Every feature this refresh adds lands in the uncovered region, and each reproduces a past shape
unless the missing axis is added:
- **§Q contradicts `member_set_immutable`** — merging stage-Q2 without re-stating that theorem
  (with the IMMS N-of-N + consent as the new precondition) leaves a **false theorem in the audited
  corpus** (mechanism B in its purest form).
- **Partial withdrawal** is an L1 gate with `cancelPartial` *un-theoremed* and no channel-state
  counterpart — the exact "categorized not proved" gap of V-class B, and a cancel with no theorem
  is where a gate-8 honest-exit failure would hide (A).
- **The close lifecycle** exists in Lean only as a version-max fold; adding intent/cancel/deadline
  states without an R1 honest-exit property reproduces the gate-8 class directly (A).

Therefore Part 3 states every new property in BOTH directions — soundness (no bad state accepted)
AND an R1-style honest-exit/availability lemma — and re-states `member_set_immutable` rather than
letting §Q silently falsify it.

## Part 3 — Verification plan (staged; lands as subsequent commits)

The user directed all four scopes be covered — §Q member-set update / key rotation, the close
lifecycle cases, partial withdrawal, and the inter-channel credit path — in the spec-side Lean
(`doc/architecture-audit/`), with the gate-8 lesson applied: **every property stated in both
directions** (soundness AND an R1 honest-exit/availability lemma), and `member_set_immutable`
re-stated rather than silently falsified.

New model file: `doc/architecture-audit/ChannelSafetyQ.lean` (added to `lakefile.lean` as a lib),
building on the `ChannelSafety2` plaintext-Regev abstraction (the level where member keys and tags
already exist). Staged so each stage is a self-contained, `lake build`-green commit.

### Stage V1 — member-set updates / key rotation (§Q)
Model `MemberSet` (a `Fin n → Key` prefix + version), `MemberSetOp` (AddCosigner / RotateKey), and
`applyUpdate`. Theorems:
- **`update_requires_prev_nofn`** — no state with a new member root is reachable without the
  previous set's full N-of-N over the IMMS digest (soundness).
- **`rotate_requires_self_consent`** — a RotateKey needs the slot's current key's IMKR signature;
  the affected member's veto is inherent (soundness; the "change your own key with your own
  signature" invariant made explicit).
- **`rotate_preserves_regev`** — the Regev key (thus every balance ciphertext) is unchanged by
  rotation; balances stay decryptable (a §Q-6 safety obligation, and an honest-availability lemma).
- **`update_preserves_validity` / `update_conserves_total`** — an applied update moves no value and
  keeps the balance invariant (the delegate slot-shift moves rows, does not alter them).
- **`member_set_immutable_unless_authorized`** — the RE-STATEMENT: the registered root is preserved
  across every transition WHOSE action kind is not MemberSetUpdate, and advances ONLY under an
  authorized update. This supersedes `UpdateUser.lean:47-51`'s `member_set_immutable`, which is
  updated in the same commit to carry the `¬isMemberSetUpdate` hypothesis (keeping the audited
  corpus internally consistent).
- **R1 `honest_member_can_rotate`** — a member holding its current key CAN produce an update the
  gate accepts (the availability direction; guards against a fail-closed rotation that no honest
  member can ever complete).

### Stage V2 — close lifecycle cases
Lift the abstract `CloseGame` to a `CloseState` machine with `status ∈ {Open, Intent, Finalized,
Cancelled}`, an `epoch`/`deadline`, and the transitions `requestClose`/`submitCloseIntent`/
`cancelClose`/`finalizeClose`. Cases to prove:
- **`no_double_close`** — a channel cannot be finalized twice; a second intent at ≤ the finalized
  version is rejected.
- **`cancel_only_before_finalize`** — cancel is reachable only in Intent within the challenge
  window; `cancelClose` after `finalizeClose` is unreachable (and the mirror: it IS reachable
  before — R1).
- **`close_at_stale_state_loses`** — an intent at version v is beaten by any co-signed state at
  version > v (the challenge-latest-wins property, but now over the status machine, not just a
  version fold).
- **`non_member_cannot_close`** — `requestClose` requires `isMemberRecipient` (the on-chain gate,
  lifted).
- **`freeze_nonce_monotone`** — `close_freeze_nonce` strictly increases across a cancel→reopen, so
  a revived channel cannot replay a stale close intent.
- **R1 `honest_close_terminates`** — an honest member whose state is the latest CAN drive
  intent→finalize to a payout (the gate-8 honest-exit obligation for the close path specifically —
  this is the property whose absence hid V4).

### Stage V3 — partial withdrawal (channel-state side)
Give partial withdrawal the channel-state counterpart the L1 model lacks:
- **`partial_debits_exactly_once`** — the burn leg debits the channel fund by exactly the withdrawn
  amount, once (conservation on the source).
- **`partial_cancel_restores`** — `cancelPartial` returns the channel to its pre-intent fund (THE
  theorem `cancelPartial` currently lacks; its absence is where an honest-exit or a double-spend
  would hide).
- **`partial_claim_single_use`** — the settled burn can be claimed on L1 at most once (mirrors the
  L1 `partial_chain_key_single_use`, now tied to the channel-state burn nullifier).
- **R1 `honest_partial_withdraw_pays`** — the honest burn→settle→claim path reaches a payout.

### Stage V4 — inter-channel credit path (§P included)
Close the weakest link:
- **`credit_no_double`** — the same settled tx credits the destination at most once (the mechanism
  `lean-safety-proof2.md:97-99` flags as UNMODELED — this is the headline gap).
- **`aux_binds_leaf`** — model F-AUX-1 (`aux_data == tx_leaf_hash`) as an in-model invariant so the
  off-circuit co-sign check is represented, not assumed away.
- **§P `agg_leaf_authorized`** — every leaf in an aggregated tx tree carries its sender's IMI5
  signature and the tree root recompute is complete (no unsigned/foreign leaf), lifting §P-3's
  five-point checklist into the model.
- **`interchannel_joint_conservation`** — extend `interChannel_conservation_bound` to the multi-leaf
  (§P) shape (currently one dest at a time, M8).

### Cross-cutting: close the process gaps (Part 2)
- Add `lake build` of BOTH Lean projects to CI (the R2/R6 enforcement the corpus never had —
  today nothing runs it).
- Each new stage's file header declares its trust base and its DEFERRED items explicitly (the
  discipline that made the existing headers honest), so the "categorized not proved" gap (mechanism
  B) cannot recur silently.

**Order:** V1 first (it resolves the live contradiction), then V2, V3, V4. Each is a separate
commit with its own `lake build`-green proof; this document's status table is updated as each lands.
