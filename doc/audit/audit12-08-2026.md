## 0. What the component is, and what it must satisfy

`Plonky2GateEvaluator.evalCombinedFlat` is the Solidity re-implementation of plonky2's
`evaluate_gate_constraints`: it is the terminal of the MLE verifier's Φ_gate sumcheck
(`Plonky2GateEvaluator.sol:83-90`). For every gate family present in the circuit it must
compute the *same* constraint vector, at the same slot indices, that the Rust prover's
quotient polynomial was built from. `_evalExponentiation` is the branch for
`ExponentiationGate` (gate id 8, `Plonky2GateEvaluator.sol:56`), plonky2's
square-and-multiply exponentiation ladder.

The correctness bar is two-sided and both sides are fund-relevant:

* a **missing or weakened** term ⇒ L1 accepts a witness plonky2 would reject
  (soundness);
* an **extra or wrong** term ⇒ L1 rejects honest proofs (completeness) — for this gate
  that means every withdrawal-claim proof becomes unverifiable, i.e. an honest-exit
  availability failure.

The gate is on the live path: both real proof fixtures carry a gate-8 row with
`num_power_bits = 66`,

```
$ python3 -c "import json;d=json.load(open('contracts/test/data/withdrawal_claim_mle.json'));\
print([g for g in d['gates'] if g['gateId']==8])"
```

yields `numOrConsts: 66`, `numConstraints: 67`, `selectorIndex: 1`,
`groupStart: 6`, `groupEnd: 10`, `gateRowIndex: 9` — identically in
`contracts/test/data/post_close_claim_mle.json`.

### The constraint set

From `exponentiation.rs:108-125`:

```
for i in 0..n:
    prev     = (i == 0) ? 1 : intermediate[i-1]^2      (:109-113)
    cur_bit  = power_bits[n - i - 1]                   (:115-116)  // LE wires, BE ladder
    computed = prev * (cur_bit*base + (1 - cur_bit))   (:118-120)
    acc[i]  += filter * (computed - intermediate[i])   (:121)
acc[n] += filter * (output - intermediate[n-1])        (:124)
```

Wire layout (`exponentiation.rs:60-77`): `base = 0`, `power_bit(i) = 1 + i`,
`output = 1 + n`, `intermediate(i) = 2 + n + i`; `num_wires() = 2n + 2` (`:190-192`),
`num_constraints() = n + 1` (`:202-204`), `num_constants() == 0` (`:194-196`).

## 1. Equivalence with the Rust gate

`num_constants() == 0` (`exponentiation.rs:194-196`) is what makes the dispatcher's
plumbing trivial for this gate: plonky2 strips the first `num_selectors` entries of
`local_constants` only (`Gate::eval_filtered` → `vars.remove_prefix`), and this gate
reads no constants, so the `wires` slice handed to `_evalExponentiation`
(`Plonky2GateEvaluator.sol:199-204`) is the gate's `local_wires` with no offset. Every
index below is therefore a direct comparison.

| Rust (`exponentiation.rs`) | Solidity (`Plonky2GateEvaluator.sol`) | Equal because |
|---|---|---|
| `local_wires[wire_base()] = [0]` (`:60-62`, `:95`) | `base := mod(mload(wPtr), p)` (`:629`) | index 0 |
| `power_bits[n-i-1] = local_wires[1 + (n-i-1)] = local_wires[n-i]` (`:65-68`, `:116`) | `mload(add(wPtr, mul(sub(n, i), 0x20)))` (`:644`) | `1 + (n-i-1) = n-i` |
| `not_cur_bit = ONE - cur_bit` (`:118`) | `addmod(1, sub(p, curBit), p)` (`:647`) | `curBit < p` after `:644`'s `mod` |
| `cur_bit * base + not_cur_bit` (`:119`) | `addmod(mulmod(curBit, base, p), notCurBit, p)` (`:651`) | field ops |
| `prev * mul_by` (`:118-120`) | `mulmod(prev, mulBy, p)` (`:652`) | field ops |
| `intermediate_values[i] = local_wires[2+n+i]` (`:74-77`) | `ivBase = wPtr + (2+n)·32`, `mload(ivBase + i·32)` (`:636`, `:654`) | index `2+n+i` |
| `constraints.push(computed - intermediate[i])` (`:121`) | `acc[i] += filter · (computed − iv)` (`:658-660`) | see §1.3 |
| `intermediate_values[i-1].square()` (`:112`) | `prev := mulmod(iv, iv, p)` at loop bottom (`:665`) | see §1.2 |
| `output = local_wires[1+n]` (`:70-72`, `:99`) | `mload(add(wPtr, mul(add(1, n), 0x20)))` (`:670`) | index `1+n` |
| `constraints.push(output - intermediate[n-1])` (`:124`) | `acc[n] += filter · (output − lastIv)` (`:671-674`) | index `n` |

The three sibling Rust evaluators agree, so any of them is a valid oracle:
`eval_unfiltered_base_packed` (`:210-243`) is the same expression tree over `P::ONES`;
`eval_unfiltered_circuit` (`:141-180`) uses
`select_ext_generalized(cur_bit, base, one)`, and
`gadgets/select.rs:22-30` expands that to `b·x − (b·y − y) = b·(x − y) + y`, i.e.
`cur_bit·base + (1 − cur_bit)` — the *generalized* selector, which does **not** assume
`cur_bit ∈ {0,1}`. This matters for §1.4.

### 1.1 The LE→BE index flip

`wire_power_bit(i) = 1 + i` is documented as *little-endian* (`exponentiation.rs:64-68`),
but the ladder consumes bits most-significant-first, so step `i` reads
`power_bits[n - i - 1]` (`:115-116`). Composing the two, the wire actually read at step
`i` is `local_wires[n - i]`, and that is what `Plonky2GateEvaluator.sol:644` computes —
a single `sub(n, i)`, with the `+1` of `wire_power_bit` and the `−1` of the flip having
cancelled. The cancellation is the reason a naive "port `wire_power_bit` then flip"
reading of the Solidity looks off by one; the comment at `:641-643` records the
composition explicitly.

That the flip is the *correct* one is proved rather than argued:
`Zkp/Core/Exponentiation.lean` `output_pow` establishes that a satisfying witness with
boolean bits has `output = base ^ (Σ_j bit_j · 2^j)` with `bit_j` read from wire
`power_bit(j)` — i.e. the little-endian value. Had the flip been dropped or shifted, the
ladder would compute `base` raised to the bit-reversed exponent and the theorem would
not close. The index bookkeeping in the proof is carried as `i + j + 1 = n` rather than
as `Nat` subtraction, so `n - i - 1 = j` is discharged at every step instead of assumed
(`Exponentiation.lean`, `ivOf_pow`).

### 1.2 `prev` squares the WIRE, not the previous `computed`

Rust reads `intermediate_values[i-1].square()` (`exponentiation.rs:112`) — the
*intermediate-value wire*. It does **not** square the value the previous constraint
computed. On a satisfying witness the two coincide (that is exactly what constraint
`i-1` asserts), so no satisfying test vector can tell them apart; on an arbitrary wire
assignment they are different functions, and a port that squared `computed` would be a
silent soundness change.

The Solidity port carries `prev` as a loop register (`:633` init, `:665` update) rather
than indexing, and the register is assigned from `iv` — the value loaded at `:654` —
with the comment at `:662-664` naming the distinction. Two facts pin this down formally:

* `Exponentiation.lean` `sat_iv_eq_ivOf` / `sat_output_determined`: on any satisfying
  witness the intermediate-value wires are forced to the ladder values, so the prover has
  no freedom and the two readings agree.
* `Exponentiation.lean` `prev_variants_differ`: an explicit witness on which the
  wire-squaring and computed-squaring evaluators disagree. This is the formal statement
  of "differential vectors for this gate must include *unsatisfying* assignments" — the
  satisfying ones provably cannot separate the correct port from this mutation.

Separately, the register formulation itself is proved equivalent to the indexed Rust
spec: `solLoop_eq` states, and proves by induction, the loop invariant *on entry to
iteration `i` the register holds `prev iv i`*; `solEval_eq_rust` composes it with the
output slot to give the whole constraint vector, including that slots outside `0..n` are
left untouched.

### 1.3 Accumulation semantics

Rust's `evaluate_gate_constraints` writes `constraints[i] += filter · c_i` across all
gate rows sharing a slot. `Plonky2GateEvaluator.sol:660` and `:674` are `+=`
(`addmod(mload(slot), …)`), and `perIdxAccum` is zero-initialised once per call
(`:132`) and reduced with α-powers afterwards (`:242-249`). `_evalExponentiation` writes
slots `0..n` and nothing else — proved as the `else acc t` branch of `solLoop_eq` and
tested (`ZZAdversarialExpProbe.t.sol:166-169`).

`filter = 0` must contribute nothing, which is what the dispatcher relies on when it
skips a de-selected row (`:147-149`). `Exponentiation.lean` `solEval_filter_zero` proves
the evaluator is the identity on the accumulator at `filter = 0`.

### 1.4 The deliberate absence of a booleanity constraint — and why it is correct

The gate does **not** constrain `power_bits[j] ∈ {0,1}`. `Exponentiation.lean`
`sat_for_any_bits` proves the constraint system is satisfiable for *every* power-bit
assignment: given any `b`, the ladder values themselves are a satisfying witness. So a
Solidity evaluator that "hardened" the port by adding `b·(b−1) = 0` would reject
witnesses the Rust prover legitimately produces — a completeness break, and on this path
that means no withdrawal claim verifies. The `SECURITY` note at
`Plonky2GateEvaluator.sol:576-583` states this; vector V4 in the committed test suite
(`contracts/test/ExponentiationGate.t.sol:101`, rationale at `:67-82`) is the regression
lock that stops such a change from landing silently.

Mirroring the omission is correct because booleanity is established elsewhere, and both
places are themselves verified on-chain:

1. **Every power-bit slot is connected to something already boolean.**
   `plonky2/src/gadgets/arithmetic.rs:248-268` (`exp_from_bits`) takes `BoolTarget`s,
   pads the vector to `num_power_bits` with `_false()` (`:253`, `:258-259`), and then
   `connect`s slot `i` for **every** `i` in `0..num_power_bits` (`:264-266`). There is no
   unconstrained slot: a caller supplying fewer bits than the gate's width gets the
   remainder pinned to the constant zero, not left free.
2. **Where the booleanity actually lives.** A `BoolTarget` from `split_le` is a
   `BaseSumGate<2>` limb — `plonky2/src/gadgets/split_join.rs:25-40`, with the comment at
   `:38` recording exactly this ("`new_unsafe` is safe here because `BaseSumGate<2>`
   forces it to be in `{0,1}`") — and `BaseSumGate`'s constraint list contains
   `Π_{k<B} (limb − k)`, i.e. `limb·(limb−1)` at `B = 2`
   (`plonky2/src/gates/base_sum.rs:68-81`). A `BoolTarget` from
   `add_virtual_bool_target_safe` instead carries `assert_bool`
   (`plonky2/src/gadgets/range_check.rs:55-58`), an `ArithmeticGate` term. `_false()` is
   `self.zero()` (`plonky2/src/plonk/circuit_builder.rs:640-642`), a routed constant, so
   its value is pinned by `ConstantGate`.
3. **Both halves are checked by the same L1 verifier.** `BaseSumGate` is gate id 9 and is
   evaluated at `Plonky2GateEvaluator.sol:205-206` → `_evalBaseSum` (`:680-686`);
   `ConstantGate` is id 1 → `_evalConstant` (`:163-171`); `ArithmeticGate` is id 3
   (`:154-162`). The `connect` itself is a copy constraint, and the copy/permutation
   argument is verified on-chain by the v2 logUp machinery in `MleVerifier.sol`
   (`:198-251`, terminal at `:355-364`), whose identity-permutation MLE is pinned to the
   VK-supplied `kIs` / `subgroupGenPowers` (`MleVerifier.sol:136-144`).

So the chain "bit wire is boolean → it is `connect`ed into the exponentiation slot →
therefore the exponentiation slot is boolean" is closed entirely by constraints the L1
verifier already evaluates. In the Lean model this appears as the named hypothesis `hb`
of `output_pow` — imported, explicit in the signature, never an axiom, per the house rule
at `doc/audit/zkp/Zkp/Core/Field.lean:62-66`.

### 1.5 Base field vs. extension field

Rust's `eval_unfiltered` returns `F::Extension` values, while the Solidity evaluator
accumulates only the `c0` component (`Plonky2GateEvaluator.sol:120-129`, `c1` left at 0).
For this gate that is exact rather than an approximation: every input is an MLE
evaluation of a base-field witness column, lifted into the degree-2 extension, and the
gate's expression tree uses only `+`, `−`, `*`. The base field is a subring of the
extension, so the result has zero `c1` component by construction. No extension-specific
arithmetic (`EXT2_W`, `:63-64`) is reachable from this branch — contrast
`_evalArithmeticExt` / `_evalMulExt`, which do use it.

## 2. The descriptor cannot be forged

`_evalExponentiation` is driven entirely by `GateInfo.numOrConsts` = `num_power_bits`
(`Plonky2GateEvaluator.sol:201`). If a prover could choose that number freely it could
pick a descriptor under which a garbage witness satisfies a shorter (or differently
shaped) constraint set. It cannot:

* Every field of every `GateInfo` — including `numOrConsts` and `numConstraints` — is
  hashed by `MleVerifier.computeGatesDigest` as a raw `calldatacopy` of the whole array
  (`MleVerifier.sol:617-637`, layout documented at `:605-616`; the per-element 288-byte
  calldata stride is spelled out at `:614-616`).
* `verify` recomputes that digest before doing any proof work and reverts on mismatch
  (`MleVerifier.sol:169-178` → `_requireGatesDigest`, `:639-650`).
* The expected digest is read from **storage**, not calldata:
  `contracts/src/IntmaxRollup.sol:1883` passes `vk.gatesDigest`, where `vk` is the
  storage pointer selected at `:1870` (`withdrawalMleVk` or `mleVk`) and the field is
  declared in the `MleVk` struct at `:294`. Nothing on the calldata path can influence
  it — `_verifyMleWithVk` takes only the proof and a bool.

Consequently the length `require`s inside `_evalExponentiation` (`:609`, `:612-615`,
`:617-620`) are defence-in-depth rather than the primary control: on the production path a
descriptor that disagreed with the VK never reaches them. They still matter, because
`_evalExponentiation` is `internal` (the rationale is recorded at `:595-598`) and because
Yul `mload`s bypass Solidity's array bounds checks — see §4.

Note also that `numConstraints` is carried in the descriptor and hashed, but is not read
by this branch; only `numOrConsts` drives evaluation, and `acc.length` is checked
directly (`:617-620`). A descriptor whose `numConstraints` disagreed with `n + 1` cannot
change what is computed, and cannot pass the digest check either.

## 3. Field-arithmetic canonicalisation

Goldilocks `P = 0xFFFFFFFF00000001` (`:623`). Yul's `sub(p, x)` is 256-bit and silently
wraps if `x ≥ p`, which is the `K = 2^256 mod P` injection class documented on
`_evalConstant`. Every prover-supplied wire this function negates is self-reduced first:

| Value | Reduced at | Negated at |
|---|---|---|
| `curBit` | `:644` | `:647` (`sub(p, curBit)`) |
| `iv` | `:654` | `:658` (`sub(p, iv)`) |
| `lastIv` | `:671` | `:672` (`sub(p, lastIv)`) |
| `base` | `:629` | never — only `mulmod` (`:651`) |
| `output` | `:670` | never — only `addmod` (`:672`) |

`prev` is initialised to the literal `1` (`:633`) and thereafter assigned
`mulmod(iv, iv, p) < p` (`:665`), so it is canonical by construction. `filter` is not
reduced here, but `_computeFilter` returns a value `< p` (`:279-299`, itself defensively
reducing its selector input at `:282`) and every use is inside `mulmod`.

This is defence in depth: `MleVerifier._requireCanonicalProofInputs`
(`:652-681`) already rejects any non-canonical entry in
`witnessIndividualEvalsAtRGateV2` — the array that becomes `wires` — before
`_verifyCore` runs. The self-reduction means the gate evaluator is correct even if that
boundary check were bypassed or the function called directly.

## 4. Fail-closed behaviour

**Malformed parameters.** `_evalExponentiation` validates before any Yul runs:
`n ≥ 1` (`:609`, because `exponentiation.rs:124` indexes `intermediate_values[n-1]`
unconditionally, so `n = 0` is not a representable gate instance in Rust),
`wires.length ≥ 2n + 2` (`:612-615`) and `acc.length ≥ n + 1` (`:617-620`). A very large
`n` reverts in Solidity's checked arithmetic while computing `2 * numPowerBits + 2`,
before any `mload`. On the production path `n` is a `uint16` so overflow is unreachable;
the check is what makes the `internal`-visibility entry point safe.

**Genuinely unsupported gates.** The dispatcher's `else` branch still reverts with
`"unsupported gate with non-zero filter"` (`Plonky2GateEvaluator.sol:230-236`); only gate
id 8 moved out of it, and `contracts/test/ExponentiationGate.t.sol:310-317` locks that in.
The remaining unsupported families are `LookupGate` / `LookupTableGate` (`:32-36`). Note
the revert is gated on `filter != 0` (`:147-149`), matching plonky2's `eval_filtered`:
a de-selected row of an unsupported gate contributes nothing and must not revert.

The same fail-closed property is enforced one layer earlier, in Rust, so a circuit that
drifts out of the supported set is caught at fixture-generation time rather than on L1:

* `plonky2_mle::fixture::classify_gate` maps any unrecognised `gate.id()` to the sentinel
  `255` (`contracts/lib/polygon-plonky2/mle/src/fixture.rs:449-512`, gate 8 recognised at
  `:480-481`, sentinel at `:511`). A `255` is a well-formed `u8` that hashes into a
  perfectly valid `gatesDigest`, so it is invisible to every check except the on-chain
  revert.
* `src/utils/mle_prover.rs:106` declares `SOLIDITY_SUPPORTED_GATE_IDS = [0..13]` and
  `:111` names the sentinel; `check_on_chain_evaluable` (`:113-146`) rejects a fixture
  containing either an unsupported id or a silently-truncated descriptor field.
* `tests/mle_gate_support.rs` *derives* the supported set from the `GATE_* = <id>`
  constants the Solidity dispatcher actually branches on and fails if it disagrees with
  the Rust constant (`:123-152`), and separately asserts the sentinel is rejected
  (`:323-334`). Editing one side without the other is a test failure.

### 5.2 Mutation matrix

A 17-mutation matrix over `_evalExponentiation` was run against the 73-vector probe. The
harness edits the submodule source in place, restores it, and — importantly — **verifies
each mutation was actually applied before running the suite**: it checks the anchor text
occurs exactly once, that the on-disk md5 changed, and that the mutated text is present,
reporting `APPLY-ERROR` instead of a misleading `SURVIVED` otherwise. Mutations, by name:
`M1_prev_uses_computed`, `M2_no_le_be_flip`, `M3_output_offby1`, `M4_ivbase_offby1`,
`M6_notcurbit_wrong`, `M7_prev_init_zero`, `M8_no_reduce_curbit`,
`M9_overwrite_not_accum`, `M10_no_reduce_lastiv`, `M11_drop_output_constr`,
`M12_filter_ignored`, `M13_out_filter_ignored`, `M14_no_reduce_base`,
`M15_no_reduce_iv`, `M16_no_reduce_output`, `M17_prev_not_squared`,
`M18_curbit_offby1`.

**15 are semantically distinct and are caught.** The separating property for each:

| Mutation | Separated by |
|---|---|
| `M1_prev_uses_computed`, `M17_prev_not_squared` | the unsatisfying / `prevdisc_` vectors (§1.2) |
| `M2_no_le_be_flip`, `M18_curbit_offby1` | any vector with an asymmetric bit pattern |
| `M3_output_offby1`, `M4_ivbase_offby1` | wire-index change ⇒ wrong constraint values |
| `M6_notcurbit_wrong`, `M7_prev_init_zero` | direct value change on the happy path |
| `M8_no_reduce_curbit`, `M10_no_reduce_lastiv`, `M15_no_reduce_iv` | `test_noncanonical_wires_equivalent` (`:137-152`) — each feeds a `sub(p, ·)` |
| `M9_overwrite_not_accum` | `test_accumulates_not_overwrites` (`:156-171`) |
| `M11_drop_output_constr` | slot `n` in `test_diff_vs_rust_filter1` (`:109-119`) |
| `M12_filter_ignored`, `M13_out_filter_ignored` | `test_diff_vs_rust_filter_scaled` (`:121-134`) |

**2 are provably equivalent to the original**, so no test can catch them, and this is a
proof from the code rather than a test result. Both remove a `mod(_, p)` that is
redundant because the value's *only* consumer is already a full-precision modular
operation:

* `M14_no_reduce_base` — `base` (`:629`) is consumed exactly once, inside
  `mulmod(curBit, base, p)` (`:651`); `mulmod` reduces both operands.
* `M16_no_reduce_output` — `output` (`:670`) is consumed exactly once, inside

## 6. Formal model

`doc/audit/zkp/Zkp/Core/Exponentiation.lean` (new) transcribes both evaluators over the
abstract `CField` of `Core/Field.lean` and proves the following. No characteristic
assumption, no field inverse, and no Goldilocks-specific fact is used, so each theorem
holds for every field the model admits.

| Property | Theorem |
|---|---|
| The Solidity register-carrying loop computes the indexed Rust constraint vector, and touches no other slot | `solLoop_eq`, `solEval_eq_rust` |
| `filter = 0` is the identity on the accumulator | `solEval_filter_zero` |
| The gate imposes **no** booleanity: satisfiable at every power-bit assignment | `sat_for_any_bits` |
| A satisfying witness's intermediate-value wires are forced; the output is determined by `(base, bits)` | `sat_iv_eq_ivOf`, `sat_output_determined` |
| Wire-squaring `prev` ≠ computed-squaring `prev` as functions (explicit separating witness) | `prev_variants_differ` |
| Under an imported booleanity hypothesis, `output = base ^ (Σ_j bit_j · 2^j)` — LE wires, BE ladder | `ivOf_pow`, `output_pow` |

Supporting: `fpow_add`, `leValFrom_shift` (the LSB-peel identity that the squaring step
realises).

## 7. Assessment

`_evalExponentiation` and its dispatcher branch compute exactly the constraint set of
`ExponentiationGate::eval_unfiltered`, at the correct slot indices, with the correct
accumulation and filter semantics, over canonicalised field elements, and fail closed on
every malformed parameter reachable through the `internal` entry point. The descriptor
that parameterises it is pinned to the storage VK. The absence of a booleanity constraint
matches the reference implementation and is correct: adding one would break completeness,
and the property it would assert is already established by gates the same verifier
