# INTMAX3 — Pre-release security audit (2026-08-28)

**Base:** branch `claude/live-balance-validity-finalize-b73981`, HEAD `3838d04` (= `main`).
**Method:** nine parallel deep-read passes (Manager / Verifier+Rollup / close+cancel circuits /
claim circuits / state-update verifier + §Q circuit / validity circuit §Q+M2′ / Lightning-Network
protocol lens / audit-corpus digest / re-sweep of the 2026-08-12 exit-path findings at HEAD),
each required to refute its own candidates before reporting. Every finding below was then
**independently re-verified against the code** before being written down; the refuted list is kept
because knowing what was checked and held is part of the result.

**Baseline at audit time:** `forge test` 332/332 green; both Lean corpora `lake build` green.

### Deliberately NOT fully closed in round 1 (carried, with the reason)

- **H-4 is partial.** Rejecting the generator case does not stop `vanishingG2 = k·G2` for `k = 2,3,…`,
  nor a forged `lagrangeBasisG1` driving `lhs = ∞`. The complete fix is an immutable trusted-setup
  store, i.e. a verifier redesign. Recorded in the file header as a **must-land-before-production**
  item rather than overclaimed. The real pairing branch is also untestable here: BLS12_PAIRING at
  precompile `0x11` is unavailable in Foundry 1.5.1 (empirically confirmed).
- **H-2 took the freeze, not the pinning form.** Pinning `regev_pk_digests[i] ==
  poseidon_digest(regev_pks[i])` would make the repo's own corpus non-compliant — 21 sites across 10
  files build states with all-zero digests on ACTIVE slots. **Residual: a malicious genesis assembler
  can still seed a wrong digest, which the freeze then faithfully preserves.** Closing it needs a
  genesis-side check plus a corpus migration.
- **H-6 residual:** a close that actually *settles* at a pre-burn state still strands the burn, because
  paying it would be the double-draw the gate exists to prevent. No gate both pays the burn and avoids
  the double-draw; the defence is the challenge game, and the honest burner holds the burn state.
- **M-11's on-chain check is still absent.** `_verifyMsuMle` performs no runtime rail-agreement check;
  coverage now extends only to deployments made by `DeployCloseCli.s.sol`. Fail-closed (a divergence
  rejects proofs rather than accepting foreign ones), so the exposure is liveness.
- **Untouched by round 1:** H-7, H-8, M-2, M-4, M-5, M-8, M-9, M-10 and D-1.

## REMEDIATION STATUS — round 2 (2026-08-28)

A red team attacked the round-1 close-lifecycle fixes and landed four findings. All four are closed in
`ChannelSettlementManager.sol`. The adversarial PoCs are preserved as regression pins in
`contracts/test/CloseLifecycleRedTeam.t.sol`; each `test_ATTACK_*` body is unchanged up to the call
that used to succeed, which now carries the guard's own revert selector. Every guard was
mutation-checked: removing it makes its pin fail again.

- **A1 (HIGH) — `cancelClose` had no anti-replay, and C-3 turned that from harmless into a weapon.**
  C-3's era restore was correct but made eras *cyclable*, which made one cancel proof a **reusable
  capability**: a non-member replayed the same `(closeIntentDigest, revivedStateVersion)` every round
  (measured: 25 rounds in 15,000 s, under 9% of one 172,800 s H-3 horizon), so H-3 bounded a single era
  and nothing across them. **Fix:** `highestCancelledRevivedStateVersion`, a manager-lifetime monotone
  floor requiring each cancel to exhibit *strictly newer* material. Censorship is now bounded by the
  number of distinct N-of-N-signed versions the attacker holds — a supply the honest members control by
  declining to sign — not by their gas budget.
  **Why this is not the latch round 1 rejected:** that latch gated **closes**, so satisfying it required
  the completed N-of-N set only the canceller held, converting "bricked for everyone" into "closable
  only by the attacker". This floor is read in `cancelClose` and nowhere else — `submitCloseIntent`,
  `finalizeClose` and every payout path never see it — so **exit liveness is unconditional**
  (`test_A1_floorNeverBlocksAnHonestCloseOrExit` closes with the floor at 9,999 and a v20 state).
  *Residual:* a canceller cannot reuse spent material against a fresh stale close; the remedy is
  challenge-replacement or letting the close settle — a bounded mis-allocation already inside the
  stale-close threat model, not a lockout.
- **A2 (MEDIUM) — H-3's clamp gave the last ladder rung a ZERO-length challenge window.** The
  replacement branch admitted a rung at exactly `t == closeChallengeHorizon`, and
  `min(now + challengePeriod, horizon)` then yielded `challengeDeadline == block.timestamp`, so
  `finalizeClose()` succeeded **in the same block**. **Fix:** `MIN_CLOSE_RESPONSE_SECS = 3,600`, and
  `submitCloseIntent` refuses any replacement that cannot leave that much time before the horizon.
  Derived from the repo's own measurements — a 79.3 s close proof
  (`doc/tasks/falcon-sig-phase5-notes.md:263`) plus an ~11.2M gas verify
  (`doc/architecture-audit/detail2-implementation-notes.md:294`), i.e. a multi-block inclusion bid —
  giving ~45x the proving time while costing the ladder ~2% of its span. The horizon stays absolute, so
  the guard can only end a ladder sooner, never extend it. The false claim in `_storePendingClose`'s
  comment ("without narrowing the interval the stale-close defence was sized for") is corrected in place.
- **A3 (MEDIUM) — H-6 was order-dependent (residual, not a round-1 regression).** The settlement-version
  gate is evaluated once, at burn-authorization time; authorizing while `Active` and *then* settling a
  pre-burn close reached the same double-draw from the other side. **Fix:** `finalizeClose` refuses a
  close strictly older than the `authorizedBurn{Epoch,StateVersion}` high-water mark recorded by
  `finalizePartialWithdrawal`. A single high-water pair is **exact**, not conservative: a burn at `b_i`
  is excluded from every state at-or-after `b_i`, so "V over-counts no burn" is precisely `V >= max(b_i)`
  — no per-burn list, no unbounded loop. The refusal is a **deferral, not a brick**: no burn can be
  authorized under a pending close, and both challenge-replacement and the window-unbounded
  `cancelClose` stay open, with the needed material provably in existence (the burn's own submission
  carried a close proof at `b_max`). An honest close, being at the head, is never refused. The H-6
  comment's "keeps the protection exactly" is corrected to state which order each gate covers — the
  **H-6 residual recorded above is thereby closed in this direction**; the pre-burn-settlement strand
  remains as described.
- **A4 (MEDIUM) — `cancelPartialWithdrawal` had the same replayable-proof property.** A burn is a
  historical fact, so a vetoed burner's re-submission produces a byte-identical close-intent digest; the
  strictly-newer check compares against the *pending* record, and a successful cancel deletes every
  trace — so one proof vetoed the same burn indefinitely. Composes badly with H-6: the burn is already
  debited in the signed state. **Fix:** `cancelledPartialWithdrawalRevivedVersion`, keyed **per burn
  digest**, not a global scalar. The asymmetry with A1 is deliberate and was verified by mutation: a
  shared/global mark simultaneously (i) **fails to stop the replay**, because it tracks close-lane
  activity rather than the burn, and (ii) **locks out honest cross-burn cancels**, which in this lane is
  fatal because the cancel *is* the whole remedy — a party blocked in the close lane still has the exit,
  a party blocked here watches a stale burn get authorized. *Residual:* one proof still vetoes each
  *distinct* burn once, costing that burner one `challengePeriod` before re-submission succeeds —
  bounded and non-destructive.

### Test-integrity fix (the "test that cannot fail" class)

Under `via_ir = true` the Yul optimizer treats `TIMESTAMP` as movable and CSEs two `block.timestamp`
reads across a `vm.warp`. **Empirically confirmed in this repo:**
`a = block.timestamp; vm.warp(+12345); b = block.timestamp; b - a` folds to the literal **`0`** while
both reads report the post-warp value `12346` — the read is sunk to its last use.

`test_H3_replacementLadderCannotOutrunTheEraHorizon` was the one existing test exposed to this: it read
`block.timestamp` before the ladder and again after it, so its closing
`assertLe(block.timestamp, horizon)` was at risk of degenerating to `assertLe(t, t + 2*CP)` — an
assertion that cannot fail. It now uses `vm.getBlockTimestamp()` (a staticcall, unfoldable) throughout,
plus an `assertGt(rungs, 0)` guard so the ladder cannot silently become a no-op. Swept the rest of
`contracts/test/`: `ChannelSettlementManager.t.sol:1089` is safe (its saved read is consumed as a
`vm.warp` argument, which pins it pre-warp) and `IntmaxRollup.t.sol` contains no `vm.warp` at all.

### One integration result worth recording

The M-7 liveness floor and the C-2 disable met head-on: the floor asserted `submitPostCloseClaim`
must succeed when feasible, and C-2 had just made it always revert. The invariant fired six times —
**correctly**. Rather than delete the assertion it was inverted to pin the disable, so re-enabling the
double-credit path without first landing an unapplied-incoming commitment in H1 now trips the
invariant suite instead of silently restoring the theft.

## 1. CRITICAL

### C-1 — Anyone can convict an honest submission of fraud, slash it, and roll back the chain

**`contracts/src/IntmaxRollup.sol:1782-1842`** (`_verifyFraud`), reached from the permissionless
`fraudProof` (`:1326`).

Fraud is confirmed when the committed proof's public inputs do **not** encode
`keccak256(validityPIs)` (`:1835-1836`). `validityPIs` is caller-supplied, and only four of its seven
fields are constrained (`:1815-1818`). **`validityPIs.prover` is checked nowhere** — repo-wide the only
occurrence is inside the hash itself (`:2047`) — and it is a free witness in the circuit
(`src/circuits/validity/block_hash_chain/validity_circuit.rs:89,125`), connected to nothing.

**Attack, one transaction, no privileges.** Take an honest submission's *real* proof bytes (public in
the blob) and its *real* PI values for the four checked fields; change **only** `prover` to any other
address. Commitment check passes (real bytes), KZG passes (see H-4; and an honest opening is
computable from public data anyway), PI-binding passes (real values), proof-params check passes
(`keccak(mleProof) == keccak(proofBytes)`). Then the piHash comparison necessarily fails →
`return true` → **fraud confirmed**.

**Impact.** `_truncateSubmissions` deletes the target *and every later submission*; `_slashStake`
credits the attacker 90% of each bond; `_rollbackBatch` rewinds the chain (and triggers H-1). Repeat
每 posting round: unbounded bond theft plus permanent rollup liveness kill — no submission can ever
survive to `finalize`.

**Root cause.** The submission commitment (`_submit`, `:1239`) commits
`blobHash‖proofHash‖proofLength‖stateRoot‖ethBlock` but **not** `keccak256(validityPIs)`. "The proof's
PIs differ from *these* PIs" is not evidence of fraud when the submitter never claimed them.

**Fix direction.** Either commit the PI hash at submission time and compare the fraud proof against
*that*, or constrain every field the predicate consumes (`prover` included) to a value derived from
on-chain state. A mismatch on an unconstrained field must never be a fraud trigger.

### C-2 — Post-close claim double-credits an already-applied inter-channel transfer

**`src/circuits/channel/post_close_claim_circuit.rs`** (the missing constraint is the absence of any
"this delta is unapplied" gate in `PostCloseClaimCircuit::new()`).

The circuit proves: the incoming tx hash is included in `final_settled_tx_accumulator_root`, the
receiver's slot leaf binds their Regev key, and the delta ciphertext decrypts to `amount`. It does
**not** prove the delta has not already been added into that receiver's slot ciphertext.

Two verified facts make this unconditionally exploitable rather than a corner case:

1. **Every closeable state has all incoming applied.** `CloseIntent::new` rejects a nonzero residue —
   `src/common/channel.rs:1080-1082` (`"close requires unallocated_confirmed_incoming = 0"`).
2. **The accumulator leaf survives the application.** `src/wallet_core.rs:4218` —
   `let bundle_accumulator = import_accumulator.clone();` — the receive's accounting leg keeps the
   same accumulator the import leg pushed the tx hash into.

So in *every* state that can close, the receiver's balance already contains the delta **and** the tx
hash is still in the accumulator. The two claim paths then both succeed on one entitlement:
`submitWithdrawalClaim` credits the decrypted slot balance (which includes the delta), and
`submitPostCloseClaim` credits the delta again. The nullifiers cannot collide — different maps,
different domains (`IMW2` vs `IMCK`).

Additionally, `unallocated_confirmed_incoming` is **not in the H1 preimage**
(`src/common/balance_state.rs:501-529` — verified field-by-field), so no signed commitment carries the
information a fix would need.

**Impact.** Theft of up to the received amount per absorbed incoming transfer, repeatable, no
collusion. The per-token cap is not a defence: it is a shared budget, so the loss lands on whichever
co-member claims last (`WithdrawalCapExceeded`).

**Note.** The path has no legitimate reachable use: the interrupted-receive scenario it exists for
leaves `unallocated ≠ 0`, which cannot close. Any fix must therefore decide whether to (a) commit an
"unapplied incoming" value into H1 and require the claim to open it, (b) split the accumulator into
applied/unapplied, or (c) remove the path.

### C-3 — One `cancelClose` bricks the channel forever; it is unilaterally triggerable

**Known, documented, unfixed, and absent from every findings register.**
`doc/tasks/close-detached-signing-design.md` §8.4 records it as **T-7a**: *"the channel can never be
closed again … I did not attempt to fix it."* It is not in `audit25-08-2026.md`.

The chain (each link verified):

- `close_circuit.rs:587-589` — the close PI is `state.close_freeze_nonce + 1`.
- `ChannelSettlementManager.sol:1045` — `requestClose` always does `currentCloseFreezeNonce += 1`.
- `:1074` / `:1090` — `submitCloseIntent` demands strict equality with that counter.
- `:1182-1186` — `cancelClose` restores `Active` but **does not touch the counter**.
- **No shipped code ever advances a `ChannelState.close_freeze_nonce`.** It is actively frozen:
  `block_producer.rs:678,777` and `live_balance_service.rs:1760` *reject* a changed era;
  `wallet_core.rs:2632` copies it; the only `+ 1` in the tree is `wallet_core.rs:8105`, inside
  `#[cfg(test)]` (the `cfg(test)` block starts at `:7056`).

After one cancel the counter is `k` while every producible state still carries `k-1`. Closing again
needs `requestClose` → `k+1`, which needs a state at `k` — unproducible. `submitPartialWithdrawalIntent`
dies the same way (`:1286`). There is no emergency or timeout exit in the Manager.

**It is an attack, not just a footgun.** `cancelClose` has **no `msg.sender` restriction and no
challenge-window bound** (verified: the only guards at `:1158-1172` are `pendingClose.active` and the
digest match). And `wallet_core.rs:5797-5800` advertises that *"an honest member holding a later
co-signed head can now build the cancel proof with no key material at all."* So the coordinator who
collects detached signatures (`wallet_core.rs:5042`) can withhold the completed set for `v_{N+1}`, let
an honest member close at `v_N`, then cancel with `v_{N+1}` — legal on every check — and the channel
is permanently unclosable by anyone, including the attacker.

**Impact.** All channel funds permanently locked on L1. Cost: one transaction plus one cancel proof.

**Model divergence worth recording:** `ChannelSafetyClose.lean` T7 (`cancel_bumps_freeze_nonce`) models
a cancel that advances the nonce. The contract does not. The Lean model is not the deployed machine.

## 2. HIGH

### H-1 — Every rollback permanently destroys deposits and channel registrations
`contracts/src/IntmaxRollup.sol:1979-1980`. `_rollbackBatch` restores `_pendingDepositHashChain` and
`_pendingChannelRegHashChain`, but `_postBlock` **never writes** either (verified by exhaustive grep:
the only writers are `deposit() :1022`, `registerChannel() :1128`, and these two restore lines). The
restore can therefore only ever *erase* deposits and registrations made after the batch was posted,
while `totalEscrowed` correctly does not roll back — leaving ETH credited to nobody, permanently.
For channels it is worse: `channelMemberSetCommitment` is not rolled back either, so the one-time
guard (`:1078`) still fires and the channelId is bricked forever. Reachable via C-1, via a genuine
fraud proof, or via the permissionless proof-free timeout branch (`:1348`).

### H-2 — `balance_state.regev_pk_digests` is frozen by nothing → a member's balance is strandable
`src/circuits/channel/state_update_verifier.rs:1452-1495` / `:1513-1529` freeze `recipients`,
`token_registry`, `token_count` and force `state_version + 1`, but **never compare
`regev_pk_digests` across states** (the field appears in that file only inside `#[cfg(test)]`).
`BalanceState::validate()` constrains only *padding* digests; `verify_snapshot` checks
`record.regev_pk_root`, never the balance-state copy. Any party able to propose a transition can
therefore corrupt a victim's digest; every honest co-signer's gate passes, all N sign, and the value
is committed into H1. The victim can then never produce a withdrawal claim for their own slot, and
there is no sweep function. The identical failure mode is documented and defended on the *join* path
(`src/bin/channel_member.rs:4479-4493`, "permanent … UNCLAIMABLE at close") — the transition path was
not.

### H-3 — Challenge-window ladder: each replacement resets the deadline
`ChannelSettlementManager.sol:1097` calls `_storePendingClose` on **both** the first-intent and the
challenge branches, and `:1119-1125` unconditionally sets
`challengeDeadline = block.timestamp + challengePeriod`. The strict `_isNewer` tiebreak stops
replaying the same state; it does not stop walking up the version ladder. Each legal replacement buys
another full window, so exit can be delayed for as many days as there are submittable intermediate
versions — and §M-7 batching (200 tx per co-signed round) makes versions cheap. No absolute cap
exists. `ChannelSafetyClose.lean:75-78` leaves `deadline` unchanged on `challenge`, i.e. the model
proves honest-exit termination for a machine that is not this one.

### H-4 — The KZG blob binding is vacuous at the caller's option
`contracts/src/BlobKZGVerifier.sol:205-232`. `vanishingG2` and `lagrangeBasisG1` are caller-supplied.
Setting `vanishingG2 = G2_GENERATOR` degrades the check to `π == C − I(τ)`, computable by anyone from
public points with no trapdoor. Honest provers never take that branch (the real `[Z(τ)]₂` is never the
generator), so it is purely an attacker affordance — and it makes C-1's data-availability precondition
free. The real pairing branch has zero test coverage.

### H-5 — `finalize` does not bind `submissionId` to the proof it verifies
`contracts/src/IntmaxRollup.sol:1275-1301`. The submission is only checked for existence and
non-finalization; `stateRoot`/`validityPIs`/`mleProof` are never compared against that submission's
commitment. Anyone can finalize submission *B* with submission *A*'s public proof: *B* is marked
finalized and its bond refunded **without its own proof ever being verified**, and it becomes
permanently un-slashable (`fraudProof` reverts `SubmissionAlreadyFinalized`), which also blocks
rollback of every earlier submission.

### H-6 — Partial-withdrawal era fence permanently strands an already-burned amount
`finalizePartialWithdrawal` requires the pending era to still equal `currentCloseFreezeNonce`
(`:1436-1438`), and **any** `isMemberRecipient` address — every member *and every delegate* — can
increment it with one `requestClose()` (`:1043`, `:1045`). The burn is already committed in the
N-of-N-signed state, so the amount is debited in-channel and excluded from `channelFundAmounts`,
while the L1 authorization never lands. Re-submission needs `Active` **and** a state re-signed in the
new era whose chain still ends with that burn — and under C-3 the new era is unreachable at all.
Cost to the griefer: one transaction. Also triggerable accidentally by an honest member who wants to
close.

### H-7 — Delegates have no unilateral exit *(carried forward, re-verified open at HEAD)*
`requestClose` gates on `isMemberRecipient`, written in the constructor (`:824`, `:882`) and — new —
in `applyMemberSetUpdate`'s add path (`:1008`), which requires the old cluster's N-of-N and is in any
case dead on every real deployment (M-3). The browser wallet persists only a seed and a channel id;
the claim is a 2^20 plonky2 proof that §R-1 forbids WASM from building; `src/wasm_wallet.rs` exports
no claim function. The documented delegate "exit" path (`node/delegate/branches/exit.js:59-92`) is a
REST call **to the co-signer it would be exiting from**. Delegate funds are custodial in fact.

### H-8 — Close after `cosign-l1-deposit-import` is still refused *(carried forward, re-verified open)*
`close_circuit.rs:1044-1052` `BalanceBindingMismatch`; `channel_attestation.bin` has exactly one
writer, `setup-backing` at genesis (`channel_member.rs:2335`); no re-attestation path exists
(`grep re-attest` → nothing). Deposit-into-an-existing-channel via import cannot subsequently close.

## 3. MEDIUM

- **M-1 §Q admits duplicate keys — at the CIRCUIT layer.** Neither `validate_member_set_delta`
  (`update_channel_tree.rs:169-211`) nor the circuit (`:1400-1437`) nor
  `member_set_update_circuit.rs:342-405` nor `applyMemberSetUpdate` (`:944-1006`) requires the new
  `pk_g` to differ from the other slots'. A rotate-to-duplicate is an **effective removal**, bypassing
  the explicit no-removal rule, and it falsifies the obligation `update_channel_tree.rs:116-125`
  claims to discharge ("duplicates are unrepresentable"). It also makes `signer_count` stop counting
  *distinct* signers.
  **Scope correction (2026-08-28, found while fixing):** the *wallet* co-sign gate was already
  closed — `ChannelRecord::validate()` rejects duplicate active `member_pk_gs` pairwise
  (`src/common/channel.rs:325-328`) and `verify_member_set_update` reaches it via `build_record`.
  The real exposure is therefore **circuit-only**: the circuit never sees a `ChannelRecord`, only
  `MemberLeaf` arrays, so nothing stood between an adversarial prover and the delta gates. That is
  also why a regression test must hand-build the update rather than go through `propose_rotate_key`,
  which `build_record` refuses to construct. The constructor checks distinctness (`:816`); the
  update path did not.
- **M-2 §Q has no witness path.** `block_witness_generator.rs:892,1494` hard-code
  `channel_actions: None` on every production path, so `is_member_update` is identically false and §Q
  is unreachable outside unit tests. Worse, `:1443-1448` writes `member_pubkeys_root` from the *previous*
  leaf unconditionally, so the moment channel actions are wired the daemon's authoritative base state
  diverges from the proven root on every MSU block.
- **M-3 The member-set-update VK is installed by no deploy script.** Repo-wide, `initializeMemberSetUpdateVk`
  appears only in its declaration and in one test. No script, no runbook, no CI fixture guard — and
  `DeployGuards.t.sol:434` (`…keysEveryVkARealDeploymentNeeds`), written for exactly this class,
  asserts four latches and omits this one. §Q is bricked on every real deployment (fail-closed,
  deployer-repairable). **This is the fourth occurrence of the class audit622 A-M4 first reported on
  2026-06-22.**
- **M-4 `applyMemberSetUpdate` desynchronises the rollup registry.** Nothing propagates the new set to
  `IntmaxRollup.channelMemberSetCommitment`, and `registerChannel` is one-time, so re-sync is
  impossible. The constructor's Finding-E equality (`:846-855`) — the invariant that the validity path
  and the close path authenticate the *same* signer set — becomes false for the rest of the channel's
  life with nothing detecting it.
- **M-5 `registerChannel` is a permissionless one-shot DoS.** No `msg.sender` check (`:1064`), folds
  into `_pendingChannelRegHashChain` (`:1128`), and `postBlockAndSubmit` accepts no expected-chain
  argument — so a stranger's registration between witness generation and `postBlock` desyncs the
  chain, `finalize` returns false *silently* (M-8), and **every** withdrawal is blocked while the
  griefer pays gas. Squatting a predictable channelId also bricks it permanently.
- **M-6 In-circuit cosigner floor is `≥ 1`, not `≥ 2`.** `close_circuit.rs:538` and
  `cancel_close_circuit.rs:346` assert only `active_bits[0]`; the `2..=MAX_SIG_CLUSTER` range is a

  L1 injecting `activeMemberCount`. This is the **V2 (1-of-N drain) class** as a defence-in-depth gap;

- **M-7 The invariant suite cannot fail on a liveness break.** `ChannelSettlementInvariant.t.sol:66,90,111,118`

- **M-8 `finalize` fails silently.** `IntmaxRollup.sol:1286-1291` try/catch → `return false`;

  *"A verifier that cannot evaluate a gate tells the honest user 'your proof is invalid'"* — the exact
  presentation of gate-8.
- **M-9 Unpinned close PIs make `closeIntentDigest` malleable.** `burn_tx_hash`, `close_nonce` and

## 4. Deployment-model finding (needs an explicit decision, not a patch)

**D-1 — The N-of-N is one operator, so every "N-of-N" property is vacuous as deployed.**
`node/DESIGN.md:35-37` states it plainly: *"one operator holds the N member keys (the co-signer
node)"*, and `cmd_cosign` mints every missing slot's signature in one loop
(`src/bin/channel_member.rs:4991-5002`). Consequently the §Q rotation veto ("every member, including
the affected one, holds a veto"), DLG-1 delegate protection ("enforced by member honesty at sign
time"), and the stale-close defence (which assumes an independent honest member exists to challenge)
all reduce to one process's honesty. This is disclosed only in the *operational* doc's non-goals —
`detail2.md` and the Lean trust bases state the properties over independent members without the
qualifier. That is precisely mechanism **(C)**, the one with no countermeasure in R1/R2/R6, and it is
the mechanism that produced V1.

## 5. Considered and refuted (ground covered, no finding)

- **Cancel monotonicity.** The absent on-chain `revivedStateVersion > finalStateVersion` comparison is
  supplied in-circuit and soundly anchored: `cancel_close_circuit.rs:461-467` asserts
  `close_final_state_version < revived_state_version` with a U64-correct comparator, the close operand
  is hashed into the in-circuit IMCI recompute whose output is connected to the `close_intent_digest`
  PI (`:426-459`), and L1 pins that to `pendingClose.closeIntentDigest`. An era fence
  (`revived.nonce + 1 == close.nonce`) is enforced alongside it. *(A one-line on-chain
  `require` is still worth adding as defence in depth — the property is currently single-layer.)*
- **PI limb binding, all five entry points.** Length + canonicity + strict per-limb equality, counts and
  orders verified field-for-field against the Rust `to_u64_vec`: close 103, cancel 27,
  withdrawal-claim 50, post-close 57, msu 26. Nothing the contracts act on is unbound.
- **M2′ block-level N-of-N** (the F-UPDU-2 region, and the fix for the historical 1-of-N drain).
  Attacked directly and held: `signer_count ∈ [2,8]` via two intersecting 4-bit range checks with no
  Goldilocks wrap escape; padding forced empty and active slots forced non-zero, both directions;
  the thermometer is a function of one witnessed value, not a free vector; the recomputed member root
  is connected to the leaf's committed root using the same fold the registration step used to write
  it; the aggregate VK is a build-time constant and the digest is recomputed from the block's own
  wires. The "at most one fold per block" invariant is enforced, not assumed.
- **§Q authorization.** Old leaves' `pk_g` connected slot-for-slot to the aggregate's verified pk list;
  `signer_count ↔ old_count`; commitments recomputed in-circuit and pinned by L1; the IMMS digest
  recomputed from in-circuit roots and connected to the aggregate's message. A colluding subset cannot
  install a key, drop a member, or rotate one — the affected member's own key is inside the required
  N-of-N. (M-1 is the residual.)
- **Reentrancy, CEI, and the payout cap** across the Manager and the Rollup; **nullifier replay** in both
  claim paths (check-then-set, post-close nullifier recomputed on-chain); **claim replay across a
  member-set rotation** (claims require `Closed`, updates require `Active`); **`delete pendingClose`**
  semantics on fixed arrays; **`finalizeClose` emit ordering**; **VK confusion between the close and msu
  statements** (PI lengths differ and both length-check first); **the two disabled stubs** (one caller
  each, both `external pure` reverts); **`allowMleDisabled`** on all six deploy scripts.
- **Decryption gadget malleability** (`assert_lt_q` closes the `2^31 − q` alias window; `KAPPA_BITS`
  two-sided compile-time assertion is tight) and **H1 second-preimage** (fixed-width 37-element header,
  golden-tested, every field covered).
