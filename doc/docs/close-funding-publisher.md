# Production close-funding publisher

> **RELEASE STATUS (2026-09-03): NO-GO.** The MLE/WHIR V2 compact-proof path is integrated, but
> independent cryptographic review, public-chain acceptance and the other final-audit blockers are
> not complete. `IntmaxRollup.releaseRuntime` remains chain-31337-only. This publisher cannot lift
> containment, and a successful local/mock run is not release evidence. V3 and older publisher
> journals, V1 proofs and old pending settlement state must be retired under their original
> deployment, never reinterpreted as V2.

`close_funding_publisher` consumes the immutable `full_close_funding_payout.json` produced for an
already-finalized terminal close and its named
`close_funding_validity_acknowledgement.json`. It does not create or modify a proof, circuit,
verifier key, proof encoding, proof size, or proving-time path.

For each nonempty native/ERC-20 lane it executes one atomic materialization followed by exact
per-token pulls:

1. `CloseFundingMaterializer.materializeNative(...)` or `materializeERC20(...)` validates the
   complete nonzero terminal lane, installs every Manager-derived `IPW2` authorization, and invokes
   the proof-bearing Rollup withdrawal in the same transaction. Any proof or lane failure reverts
   every authorization latch.
2. `ChannelSettlementManager.pullChannelFunds()` or `pullChannelTokenFunds(tokenIndex)` asks the
   Rollup to transfer exactly the remaining channel cap using `withdraw(uint256)` or
   `withdrawToken(uint32,uint256)`.

The Manager accepts `authorizeCloseFunding` only from its immutable materializer and additionally
requires that each token's authorization was issued and consumed before it permits a pull.
Consequently there is no externally visible authorize-before-proof window, and a pre-existing or
deliberately donated recipient-wide Rollup credit cannot impersonate the terminal proof. Any
unrelated surplus remains in the Rollup ledger; the publisher deliberately does **not** require the
recipient's aggregate pending credit to be zero or equal to a journal-time delta.

The two proof-bearing materializer selectors above are pinned in the binary to the exact
`(...,bytes compactProof)` materializer signatures; regenerate and review them whenever that ABI
changes. The publisher rejects a legacy proof-only JSON object: each lane must contain the
canonical full V2 fixture, and its proof, VK,
constructor config, Solidity ABI bytes, compact bytes, resource envelope, public inputs, and WHIR
profile must all agree byte-for-byte. The binary independently
recomputes the four non-proof Manager/Rollup pull selectors shown above and rejects discrepancies. It also
requires the calldata generated by the keyless local script to begin with the corresponding pinned
materializer selector.

The manifest path is not an authority by itself. Record the SHA-256 of the exact reviewed manifest
bytes through a separate authenticated release channel and pass that value with
`--deployment-manifest-sha256`. Reformatting otherwise equivalent JSON changes this pin and is
rejected.

`eventScanStartBlock` is an inclusive, release-reviewed lower bound at or before the Rollup,
Manager, and materializer deployments. It is not a convenience look-back window. The publisher searches from this
block to the durable finalized head in bounded chunks so it can safely discover an exact action
that another permissionless caller already completed.

At finalized state the publisher pins all six contract runtime-code hashes, every referenced
ERC-20 runtime-code hash, `manager.registry == rollup`,
`manager.closeFundingMaterializer == materializer`, `materializer.rollup == rollup`,
`manager.verifier == verifier`, `rollup.withdrawalMleVerifier == withdrawalMleVerifier`, and
`withdrawalMleVerifier.core == withdrawalMleVerifierCore`. It also checks the adapter and core
chain IDs plus the core's verification-config, circuit-config, WHIR-parameters, protocol, and
session getters against both the release manifest and every lane fixture. Token registrations,
close state/freeze nonce, finalized anchor, and every token cap remain pinned as before.

## Run

Import the funded signer into Foundry's encrypted keystore and select it by account name. There is
no raw-private-key argument.

```sh
cargo build --release --locked --bin close_funding_publisher
target/release/close_funding_publisher \
  --artifact /absolute/private/path/full_close_funding_payout.json \
  --validity-acknowledgement /absolute/private/path/close_funding_validity_acknowledgement.json \
  --deployment-manifest /absolute/release/path/close-funding-deployment.json \
  --deployment-manifest-sha256 0x<independently-reviewed-raw-file-sha256> \
  --journal /absolute/private/path/close-funding-publisher.journal.json \
  --lock-root /absolute/private/path/l1-signer-locks \
  --rpc-url https://operator-owned-archive-rpc.example \
  --account intmax-release-operator
```

The RPC must provide canonical `finalized` and historical `eth_call`, code, transaction, receipt,
block, and log data. The `latest` fallback is available only with the explicit development flag on
chain 31337 and is rejected on every public chain.

The V4 journal is a private, single-artifact capability. V3 and older journals are deliberately
not resumed because they predate the atomic V2 adapter/core identity. Its chain, deployments, artifact and ACK
hashes, channel, proposal, terminal anchor, token vector, proof calldata hashes, signer, and
canonical lock root are immutable. The parent directory is forced to mode 0700 and the journal to
0600. All INTMAX publishers that can use the same account must use the same canonical lock root;
the shared lock filename is `.intmax-l1-signer-{chainId}-{lowercaseSigner}.lock`. The same root also
holds `.intmax-l1-signer-{chainId}-{lowercaseSigner}.reservation.json`, a durable exact-intent
lease keyed by canonical journal path, action id, immutable publication binding, target, value, and
calldata hash. It is fsynced before offline signing, survives a crash after the kernel lock is
released, and is removed only after canonical finality has been fsynced into the owning journal.

## Crash, race, and reorg behavior

- Before first broadcast, each exact signed raw transaction is decoded and checked for chain,
  signer, target, value, calldata, selector, and nonce, then committed with file fsync, atomic
  rename, and directory fsync. A signer-global intent reservation is durable before signing begins;
  restart can reclaim it only for the same journal/action/calldata binding and resends only the
  exact WAL bytes. An unknown sibling nonce or foreign durable reservation stops publication.
- Completion requires a successful receipt covered by a canonical finalized checkpoint, an exact
  event emitted by the pinned contract, and the full receipt-block getter and asset-backing vector.
  Receipts, transactions, blocks, code, and getters are reread to detect unstable RPC evidence.
- The protocol is permissionless. A participant, watchtower, wrapper, or relayer may execute a
  phase first, including bundling phases into one transaction. Adoption depends on the canonical
  pinned-contract event and same-block state, not on the outer transaction's sender, destination,
  or wrapper calldata. No match and more than one exact match both fail closed.
- Adoption preserves `atomic materialize -> pull` ordering. Materialization authority is exactly
  one `CloseFundingMaterialized(manager,lane,fundingAuxData,withdrawalSetDigest)` event from the
  pinned materializer plus complete-lane Rollup payout events and same-receipt-block getters. The
  first three indexed fields are exact. `withdrawalSetDigest` must be one well-formed ABI word but
  is diagnostic: a competing valid proof may safely use different proof-private nullifiers or lane
  ordering. A donated aggregate Rollup credit without this finalized materializer evidence is
  insufficient. If an adopted action supersedes already-journaled local raw bytes, the publisher
  does not silently skip that nonce: it waits for or publishes the exact losing raw transaction
  until its canonical finalized revert consumes the nonce. That reverted receipt is also fsynced
  into the local WAL before the signer reservation can be released.
- Stored local and adopted confirmations are revalidated after restart. An unfinalized, orphaned,
  replaced, wrong-address, wrong-event, wrong-token, wrong-recipient, wrong-amount,
  wrong-nullifier, wrong-anchor, wrong-getter, or runtime-code-mutated result cannot advance the
  journal.
- Pull success is proven by the exact `ChannelFundsPulled(tokenIndex, amount, totalReceived)` event,
  `receivedChannelFunds == finalizedChannelFundAmount`, and the Manager asset/backing invariant.
  Concurrent unrelated Rollup credit may increase, so a recipient-wide pending-balance equality is
  informational only and is never used as an authority condition.

The command emits `publicE2eAttested: false` even after a complete run. A release operator must
separately record a real public-chain native and ERC-20 acceptance run, including restart and reorg
exercises. The project's accepted KZG ceremony trust assumption is unchanged by this publisher.
